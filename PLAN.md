# Green Angle — ЛК для перегона авто из Китая. Бэкенд: стек и план реализации

Документ самодостаточный: после его составления к исходному ТЗ обращаться не нужно.

## 1. Суть продукта

Платформа вместо переписки и таблиц. Три роли, одинаковая структура экранов:

| Роль               | Кто                                                    | Что делает                                                                                                                      |
| ------------------ | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `BROKER`           | Юрлицо-подборщик (партнёр), **один логин на компанию** | Видит машины, которые везутся под его клиентов; подаёт заявки на подбор; ведёт диалог по заявке. Сам машины **не создаёт**.     |
| `INDIVIDUAL`       | Физлицо                                                | То же, что подборщик, но на одного человека. Свои машины и заявки изолированы от компаний.                                      |
| `ADMIN` (супер ЛК) | Сотрудники компании                                    | Видит всё по всем клиентам. Заводит машины вручную, двигает статусы, прикрепляет вложения, отвечает на заявки, одобряет заявки. |

## 2. Стек (решение)

- **Node.js 22 + TypeScript + NestJS** (Fastify-адаптер) — модульная структура под роли/домены, DI, guards для RBAC, из коробки валидация и OpenAPI.
- **PostgreSQL 16 + Prisma** — данные реляционные (клиент → машины → шаги → вложения; заявка → сообщения), нужны транзакции (одобрение заявки) и миграции.
- **Хранилище файлов** — фото, видео, файлы, **голосовые**. Этапы 4–12 сделаны на S3-совместимом хранилище (MinIO, presigned URL); по решению заказчика переводится на диск сервера через сменный драйвер (этап A0 в §11), возврат на S3 — заменой драйвера.
- **JWT access (15 мин) + refresh (30 дней, ротация)**, пароли — argon2.
- **Socket.IO (NestJS gateway)** — живой диалог и счётчики непрочитанного. В MVP допустим polling, gateway добавляется отдельным этапом.
- **Swagger/OpenAPI** — по нему фронт сгенерирует типизированный клиент, пока макета нет.
- **Docker Compose** (api + postgres + minio), **Vitest** (unit + e2e на реальной БД; в CI — сервис Postgres), ESLint/Prettier, GitHub Actions. Актуальные версии: Node 24 LTS, NestJS 12 (ESM), TypeScript 6, Prisma 7.10.x.
- **Redis 7** — подключён: общие счётчики rate limit для всех экземпляров API (этап 12, дополнение).
Почему не Python/FastAPI: тоже подошёл бы, но единый TS-стек со схемой Prisma и сгенерированным OpenAPI-клиентом упрощает работу с фронтом.

## 3. Доменная модель

```
User(id, email, passwordHash, role[ADMIN|BROKER|INDIVIDUAL], clientId?, isActive)
Client(id, type[COMPANY|PERSON], name)            // «ООО АвтоПодбор Плюс», «Смирнов А. В.»
Vehicle(id, clientId, title "Geely Monjaro, 2024", vin? UNIQUE, currentStep 1..13, createdAt)
VehicleStep(id, vehicleId, step 1..13, completedAt?, declarationNumber?)   // история статусов
Attachment(id, key, mime, size, kind[PHOTO|VIDEO|FILE|AUDIO], uploadedById, createdAt,
           vehicleStepId?, messageId?)
Request(id, clientId, title "Chery Tiggo 8 Pro", yearFrom, budget, comment,
        status[NEW|IN_DIALOG|APPROVED], vehicleId? , createdAt)
Message(id, requestId, authorId, type[TEXT|VOICE], text?, durationSec?, createdAt)
MessageRead(messageId/requestId, userId, readAt)   // непрочитанное
VehicleStatusLog(id, vehicleId, fromStep?, toStep, declarationNumber?, changedById, changedAt)
                                                    // журнал смен статуса: кто, когда, с какого на какой
```

Правила:

- Изоляция данных: BROKER/INDIVIDUAL видят только записи со своим `clientId`; ADMIN — все. Проверка в одном месте (guard + scope-хелпер для запросов), покрыть тестами.
- `vin` nullable: машина из одобренной заявки создаётся без VIN, его заполняют позже. При ручном создании в супер ЛК VIN обязателен. Уникальность VIN — частичный unique-индекс.
- `Request.status`: `NEW` → (первое сообщение менеджера) `IN_DIALOG` → (одобрение) `APPROVED`. После `APPROVED` диалог только для чтения.

## 4. Статусная модель — 13 шагов

Список один для всех. Вложение — «ожидаемое», **не блокирует** смену статуса (в макете «ожидается фото»; пройденный шаг без вложения просто «завершён»). Строгий режим — флаг `STRICT_ATTACHMENTS`, по умолчанию выключен.

| №   | Статус                                         | Ожидаемое вложение        |
| --- | ---------------------------------------------- | ------------------------- |
| 1   | Ожидает оплату                                 | —                         |
| 2   | Получена оплата                                | файл                      |
| 3   | Выкуплен, ожидает погрузки у продавца          | фото                      |
| 4   | В транспортной компании в Китае                | видео                     |
| 5   | В пути по Китаю                                | —                         |
| 6   | Прибыла в конечную точку, экспортные документы | фото                      |
| 7   | Отправка в Россию                              | фото                      |
| 8   | Прибыла на территорию РФ                       | файл                      |
| 9   | Прибыла на СВХ, ожидает тамож. оформление      | фото                      |
| 10  | Декларация подана                              | номер декларации (строка) |
| 11  | Машина выпущена                                | —                         |
| 12  | Получение ЭПТС и СБКТС                         | фото                      |
| 13  | Готова к выдаче (СБКТС, ЭПТС)                  | фото                      |

Хранить как константу/таблицу-справочник в коде (`step`, `title`, `expectedAttachment`). Переход: ADMIN может сдвинуть на любой шаг (вперёд/назад — для исправления ошибок), каждое изменение пишется в историю. Прогресс-бар = `currentStep / 13`.

**Журнал смен статуса (`VehicleStatusLog`)** — нужен для разбора спорных ситуаций с клиентами:

- Запись создаётся при **любой** смене шага (вперёд, назад, исправление), а также при создании машины (`fromStep = null`, в т. ч. машина из одобренной заявки — `changedById` = админ, одобривший заявку).
- Хранит: машина, шаг «из» и «в», номер декларации (если менялся), **кто** (`changedById` → `User`) и **когда** (`changedAt`, серверное время).
- Запись и смена статуса — в одной транзакции; журнал **append-only** (никаких update/delete через API и код приложения).
- Пока **только хранится в бэкенде**: ни в клиентском UI, ни в супер ЛК не отображается и отдельных эндпоинтов не имеет. Просмотр — прямым запросом к БД; эндпоинт/экран добавляются позже по необходимости.
- Отличие от `VehicleStep`: тот хранит текущее состояние шагов (завершён/нет), журнал — полную хронологию изменений, включая откаты.

## 5. Диалог по заявке и голосовые сообщения (дополнение к ТЗ)

Клиенты хотят отправлять **голосовые** в диалогах заявок (и менеджер тоже).

- `Message.type = VOICE`, поля: `durationSec`, связанный `Attachment(kind=AUDIO)`.
- Поток: `POST /requests/:id/voice-upload-url` (mime, size) → клиент грузит файл в S3 по presigned PUT → `POST /requests/:id/messages {type:"VOICE", attachmentKey, durationSec}` → сервер проверяет, что объект существует, и создаёт сообщение.
- Ограничения: до 5 минут и 10 МБ; допустимые mime: `audio/webm`, `audio/ogg`, `audio/mp4` (iOS Safari), `audio/mpeg`, `audio/wav`. Длительность приходит с клиента, на сервере сверяется по самому файлу через ffprobe (реализовано, этап 12, дополнение).
- Воспроизведение: в ответе API — короткоживущая presigned GET-ссылка (≈1 ч).
- Также в диалоге: текст, вложения-варианты (фото + ссылки на объявления) — реализуем как обычные `Attachment` на сообщении и `links: string[]`.

## 6. API (REST, префикс `/api/v1`)

Auth

- `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `GET /me`

Клиентская часть (BROKER / INDIVIDUAL; ADMIN видит всё)

- `GET /vehicles` — список со статусом и прогрессом; `GET /vehicles/:id` — карточка: 13 шагов, у каждого состояние (завершён/текущий/ожидает), вложения, номер декларации
- `GET /requests`, `POST /requests` (марка/модель, год от, бюджет, комментарий), `GET /requests/:id`
- `GET /requests/:id/messages`, `POST /requests/:id/messages` (TEXT/VOICE), `POST /requests/:id/read`
- `POST /uploads/presign` — универсальная выдача presigned URL

Супер ЛК (только ADMIN)

- `GET /admin/vehicles?vin=&clientId=&step=` — поиск по VIN (по подстроке)
- `POST /admin/vehicles` (марка/модель/год, VIN, `clientId` или создание клиента, стартовый статус)
- `PATCH /admin/vehicles/:id` (в т.ч. заполнение VIN)
- `POST /admin/vehicles/:id/status {step, declarationNumber?}`; `POST /admin/vehicles/:id/steps/:step/attachments`
- `GET /admin/requests?status=&clientId=` — единая очередь заявок
- `POST /admin/requests/:id/approve` — **транзакция**: заявка → `APPROVED`, создаётся `Vehicle` (шаг 1, VIN пустой, `clientId` заявки), `Request.vehicleId` проставляется
- `CRUD /admin/clients`, `CRUD /admin/users` (создание логина подборщику/физлицу; публичной регистрации нет)

События WebSocket: `message.created`, `request.updated`, `vehicle.status_changed`.

## 8. План по этапам

Каждый этап завершается рабочим состоянием, тестами и обновлённым Swagger.

1. ✅ **Каркас** — репозиторий, NestJS, Docker Compose (postgres+minio), конфиг через env с валидацией, ESLint/Prettier, CI, healthcheck.
   _Готово, когда:_ `docker compose up` поднимает API, `/health` отвечает.
   _Итог:_ бэкенд в `backend/` (NestJS 11 + Fastify, pnpm), env валидируется zod, префикс `/api/v1`, `GET /api/v1/health`, Swagger на `/api/docs`, e2e-тест health, CI в `.github/workflows`. Проверено: `docker compose up` → health отвечает `{"status":"ok"}`. Отличия от плана: MinIO — образ `ghcr.io/coollabsio/minio` (официальные образы недоступны); бакет `green-angle` создаётся на этапе 4 (storage), отдельного init-контейнера нет.
2. ✅ **Схема БД и seed** — Prisma-схема из §3 (включая `VehicleStatusLog`), миграция, seed: 1 админ, подборщик «АвтоПодбор Плюс», физлицо «Смирнов А. В.», 3 машины (Geely Monjaro шаг 9, Chery Tiggo 8 Pro шаг 2, Zeekr 001 шаг 13), 2 заявки.
   _Итог:_ Prisma 7.10.1 (`prisma` и `@prisma/client` на одной версии; `latest` у CLI — 8.0 rc, не брать), схема `backend/prisma/schema.prisma`, клиент генерируется в `backend/generated/prisma` (в git не попадает), миграция `init` + вручную дописанные CHECK-ограничения шагов 1..13 и триггер append-only на `VehicleStatusLog`. Seed (`pnpm prisma db seed`) идемпотентен; dev-логины: `admin@greenangle.local`, `broker@autopodbor.local`, `smirnov@example.local` (пароли — в `seed.ts`, переопределяются `SEED_*_PASSWORD`). Хеш паролей — `@node-rs/argon2` (argon2id; пакет `argon2` не собирается без компилятора). Проверено на живой БД: 3 пользователя, 2 клиента, 3 машины, 39 шагов, 3 записи журнала, 2 заявки, 2 сообщения; UPDATE журнала и `currentStep=14` отклоняются. Автотестов на БД нет — CI без Postgres, интеграционные тесты появятся с этапа 3.
3. ✅ **Auth и RBAC** — логин, refresh с ротацией, guard ролей, scope по `clientId`, `/me`. Тесты: брокер не видит чужое, физлицо не видит брокерское, админ видит всё.
   _Итог:_ `POST /auth/login|refresh|logout`, `GET /me`; access JWT (15 мин) + refresh JWT (30 дней) с ротацией: запись `RefreshToken` (миграция `refresh_tokens`), атомарный отзыв, при повторном использовании старого токена отзывается вся цепочка; деактивированный пользователь не может войти/обновить токен. Глобальные `JwtAuthGuard` (исключение — `@Public()`) и `RolesGuard` (`@Roles()`), `@CurrentUser()`, scope-хелпер `clientScope`/`assertClientAccess` в `src/common/scope.ts` — единая точка изоляции по `clientId`. Проверено: 8 unit + 28 e2e на реальной БД (логин, ротация, reuse, гонка двух refresh, истечение, деактивация, роли, изоляция broker A / broker B / физлицо / админ — через тестовый контроллер, пока нет реальных сущностных эндпоинтов). В CI добавлен сервис Postgres + `prisma migrate deploy`. Попутно: проект переведён на актуальный стек — Node 24, NestJS 12 (ESM, импорты с `.js`), Vitest, ESLint, TypeScript 6; Prisma-клиент генерируется в `src/generated/prisma`. Ограничение этого этапа (access-токен не проверяет `isActive`, деактивация действовала до 15 минут) снято на этапе 11: guard берёт пользователя из БД на каждый запрос. Rate limit на логин — этап 12.
4. ✅ **Хранилище** — S3-модуль, presign PUT/GET, проверка mime/размера, модель `Attachment`.
   _Итог:_ `StorageModule` (`StorageService`: presign PUT/GET, HEAD, delete, автосоздание бакета при старте — недоступность S3 не роняет API) и `AttachmentsService` (`createFromUpload`, `toView`), `POST /api/v1/uploads/presign {kind, mime, size}` (любая авторизованная роль). Лимиты по видам в `upload-rules.ts`: PHOTO 20 МБ (jpeg/png/webp/heic), VIDEO 500 МБ (mp4/mov/webm), FILE 50 МБ (pdf/doc(x)/xls(x)/zip), AUDIO 10 МБ (webm/ogg/mp4/mpeg/wav, §5); неразрешённый mime → 415, размер вне лимита → 413; параметры mime (`;codecs=opus`) отбрасываются. Ключ объекта `{kind}/{userId}/{uuid}.{ext}`; подпись фиксирует `Content-Type` и `Content-Length` — S3 отклоняет загрузку с другим типом/размером. Регистрация вложения берёт метаданные из самого S3 (HEAD), а не от клиента; чужой ключ, ключ другого вида, несуществующий объект и повторная регистрация отклоняются. `S3_PUBLIC_ENDPOINT` — адрес для браузера в presigned URL (в Docker внутренний и внешний адреса разные). Проверено: 27 unit + 45 e2e, из них 7 против реального MinIO (загрузка по presigned URL, скачивание, отказ при несовпадении размера/типа). В CI MinIO запускается шагом `docker run` — в GitHub Actions пока не проверено. Вложения к шагам машин и сообщениям создаются на этапах 5, 7, 8 через `AttachmentsService`.
5. ✅ **Машины и статусы** — справочник 13 шагов, `GET /vehicles`, карточка с шагами и вложениями, админское создание/правка, смена статуса с историей и записью в `VehicleStatusLog` (кто/когда, в одной транзакции), номер декларации на шаге 10, поиск по VIN. Тесты: журнал пишется при смене вперёд/назад и при создании машины, откат транзакции не оставляет записи.
   _Итог:_ справочник 13 шагов в `src/vehicles/steps.catalog.ts` (заголовки, ожидаемое вложение). Клиент: `GET /vehicles?limit&offset` (список со статусом и прогрессом `currentStep/13`, ответ `{items,total}`), `GET /vehicles/:id` (13 шагов с состоянием `COMPLETED/CURRENT/PENDING`, вложения со свежими presigned-ссылками, номер декларации на шаге 10); чужая машина — 404, не 403. Супер ЛК (`@Roles(ADMIN)`): `GET /admin/vehicles?vin&clientId&step` (VIN — подстрока без учёта регистра), `POST /admin/vehicles` (VIN обязателен, формат ISO 3779, нормализуется в верхний регистр; ровно одно из `clientId` / `client`; стартовый шаг; в одной транзакции с клиентом), `PATCH /admin/vehicles/:id` (название, заполнение VIN; дубль → 409), `POST /admin/vehicles/:id/status {step, declarationNumber?}` (вперёд и назад; шаги ниже целевого завершаются, выше — открываются заново, даты уже пройденных не перезаписываются; повтор того же шага допустим только чтобы дополнить номер декларации), `POST /admin/vehicles/:id/steps/:step/attachments {key, kind}`. Каждая смена статуса и создание пишут `VehicleStatusLog` в той же транзакции; от гонки двух админов защищает условное обновление `currentStep` (проигравший получает 409, цепочка журнала остаётся непрерывной). `STRICT_ATTACHMENTS=true` блокирует переход, если у пройденных шагов нет ожидаемого вложения (список шагов в ошибке). Проверено: 96 e2e (в т.ч. изоляция broker A / broker B / физлицо / админ на реальных эндпоинтах, пагинация, гонка статусов, строгий режим, вложения через настоящий MinIO), 27 unit; на seed-данных в Docker. Тестовая очистка журнала обходит триггер append-only внутри транзакции — в коде приложения журнал по-прежнему неизменяем.
6. ✅ **Заявки** — создание клиентом, список, очередь админа с фильтрами, статусы `NEW/IN_DIALOG/APPROVED`.
   _Итог:_ клиент: `POST /requests {title, yearFrom?, budget?, comment?}` (только BROKER/INDIVIDUAL, ADMIN → 403; заявка всегда `NEW`, `clientId` и автор берутся из токена — поля `clientId`/`status`/`vehicleId` в теле игнорируются), `GET /requests?status&limit&offset` (ответ `{items,total}`, новые первыми), `GET /requests/:id` (чужая заявка — 404). Очередь админа: `GET /admin/requests?status&clientId`. Валидация: название до 200 символов, год 1990…текущий+1, бюджет ≥ 0 с точностью до 2 знаков (Decimal(14,2), в API — число), комментарий до 2000. Изоляция — тот же `clientScope`, что у машин. Пагинация вынесена в общий `PaginationQueryDto`. Переходы статусов выполняют следующие этапы: `NEW → IN_DIALOG` (этап 7, первое сообщение менеджера) и `→ APPROVED` (этап 9); поле `vehicleId` проставляется при одобрении. Проверено: 29 e2e заявок (изоляция broker A / broker B / физлицо / админ, фильтры очереди, защита от подмены полей, границы валидации), всего 27 unit + 125 e2e; на seed-данных в Docker.
7. ✅ **Диалог** — текстовые сообщения, вложения-варианты, ссылки, счётчики непрочитанного, автопереход `NEW → IN_DIALOG`, запрет писать в `APPROVED`.
   _Итог:_ `GET /requests/:id/messages?limit&before` (курсорная пагинация назад по `before`=id сообщения, ответ от старых к новым `{items, hasMore}`, у каждого сообщения `isMine`, автор `{id, role}`, вложения со свежими presigned-ссылками), `POST /requests/:id/messages {type?:"TEXT", text?, links?[], attachments?[{key,kind}]}`, `POST /requests/:id/read`, `GET /requests/unread-count`; во всех заявках появился `unreadCount`. Доступ: владелец-клиент и ADMIN, чужая заявка — 404. Правила: непустое сообщение (текст, ссылки или вложения), текст ≤ 5000, до 10 ссылок (только http/https) и до 10 вложений (PHOTO/VIDEO/FILE; AUDIO — для голосовых, этап 8), `type=VOICE` пока отклоняется. Первое сообщение менеджера (ADMIN) переводит `NEW → IN_DIALOG`; в `APPROVED` писать нельзя (409), читать и отмечать прочитанным можно. Сообщение, вложения и смена статуса — одна транзакция с блокировкой строки заявки (`SELECT … FOR UPDATE`), которая сериализует запись с будущим `approve` (этап 9 должен брать ту же блокировку); файлы проверяются в S3 до транзакции, при любой невалидной ссылке не создаётся ничего. Непрочитанное считается по каждому пользователю отдельно (в т.ч. между менеджерами): чужое сообщение без своей записи `MessageRead`. `AttachmentsService` разделён на `verify` и `createVerified` для атомарной записи. Проверено: 35 e2e диалога (в т.ч. с реальным MinIO), всего 27 unit + 160 e2e; на seed-диалоге в Docker.
8. ✅ **Голосовые сообщения** — presign для аудио, создание `VOICE`-сообщения, лимиты, выдача ссылок воспроизведения, e2e-тест всего потока.
   _Итог:_ поток из §5: `POST /requests/:id/voice-upload-url {mime, size}` (presigned PUT для AUDIO; доступ как к диалогу, чужая заявка — 404, `APPROVED` — 409) → клиент грузит файл прямо в S3 → `POST /requests/:id/messages {type:"VOICE", attachmentKey, durationSec}`. Сервер проверяет по HEAD в S3, что объект существует, ключ принадлежит пользователю и виду AUDIO, mime/размер в лимитах (`audio/webm|ogg|mp4|mpeg|wav`, параметры вроде `;codecs=opus` отбрасываются, до 10 МБ), объект ещё не использован; создаёт `Message(type=VOICE)` + `Attachment(kind=AUDIO)` в одной транзакции с блокировкой заявки. `durationSec` обязателен, 1…300 (5 минут). У VOICE не может быть текста, ссылок и вложений (400); для TEXT поля `attachmentKey`/`durationSec` игнорируются. Воспроизведение: в сообщении `attachments[0].url` — presigned GET (≈1 ч, `S3_PRESIGN_GET_TTL_SEC`). Голосовое менеджера так же переводит заявку `NEW → IN_DIALOG`, учитывается в `unreadCount`. Длительность приходит от клиента; позже её стали проверять по файлу через ffprobe (см. дополнение к этапу 12). Проверено: 28 e2e голосовых (все 5 форматов, границы 300/301 с и 10 МБ, чужой/повторный ключ, одобренная заявка, полный поток через настоящий MinIO), всего 27 unit + 188 e2e; в Docker — запись, загрузка, воспроизведение байт в байт.
9. ✅ **Одобрение заявки** — `approve` в транзакции, создание машины без VIN, связь заявка↔машина; идемпотентность (повторный вызов не создаёт дубль).
   _Итог:_ `POST /admin/requests/:id/approve` (только ADMIN) → `{request, vehicle}`. В одной транзакции под блокировкой строки заявки (`SELECT … FOR UPDATE`, та же, что у записи сообщений) создаётся машина: клиент заявки, название = название заявки, шаг 1, VIN пустой, 13 шагов, запись в `VehicleStatusLog` (`null → 1`, `changedById` = одобривший админ), затем `Request.status = APPROVED` и `Request.vehicleId`. Одобрить можно из `NEW` и из `IN_DIALOG`. Идемпотентность: если у заявки уже есть `vehicleId`, возвращается та же машина (200), дублей и новых записей журнала нет, продвинутый статус машины не откатывается; заявка в `APPROVED` без машины (рассинхрон) «чинится» — машина создаётся. После одобрения диалог только для чтения (409 на запись), клиент видит машину в `/vehicles` и `vehicleId` в заявке; админ потом заполняет VIN через `PATCH /admin/vehicles/:id`. Проверено: 17 e2e (в т.ч. 6 параллельных approve → одна машина, одна запись журнала; гонка approve с сообщениями — ни одно сообщение не проходит после APPROVED; права и изоляция), всего 27 unit + 205 e2e; собранный Docker-образ проверен вручную. `initialSteps` вынесен в `steps.catalog.ts` для общего использования с ручным созданием машины. Не покрыто тестом: откат транзакции при сбое посреди approve (искусственно вызвать сбой нечем; атомарность обеспечивает единая транзакция).
10. ✅ **Realtime** — Socket.IO gateway: события из §6, авторизация по JWT, комнаты по `requestId`/`clientId`.   _Итог:_ `RealtimeGateway` (Socket.IO на том же порту, что и API, путь `/socket.io`) + `RealtimeService` (глобальный, публикация из бизнес-сервисов только после коммита транзакции; сбой отправки не ломает HTTP-запрос). Подключение: access JWT в `auth: { token }` или заголовке `Authorization: Bearer …`, иначе `connect_error: unauthorized`; refresh-токен, просроченный и подделанный токены отклоняются; когда истекает использованный токен, сервер закрывает соединение (`io server disconnect`) — клиент переподключается с новым. Комнаты: клиент входит автоматически в `client:{clientId}`, ADMIN — в `admins`; комната заявки `request:{id}` — командой `request.join {requestId}` с ack `{ok}` / `{ok:false, error:'NOT_FOUND'|'BAD_REQUEST'}` (та же проверка доступа, что в HTTP; чужая заявка неотличима от несуществующей), `request.leave`. События: `message.created {message}` — подписчикам комнаты заявки (сообщение без `isMine`, сравнивайте `author.id` со своим); `request.updated {requestId, clientId, status, vehicleId, reason: CREATED|MESSAGE|APPROVED, at}` — своему клиенту и менеджерам (новая заявка, новое сообщение, `NEW→IN_DIALOG`, одобрение); `vehicle.status_changed {vehicleId, clientId, fromStep, toStep, toStepTitle, declarationNumber, at}` — своему клиенту и менеджерам (создание машины — `fromStep: null`, смена статуса вперёд/назад, номер декларации). Повторное `approve` и отклонённые запросы (400/403/409) событий не создают. Попутно исправлено: глобальные HTTP-guard'ы падали на WebSocket-командах — теперь пропускают не-HTTP контекст (сокет аутентифицируется один раз при подключении). Проверено: 20 e2e на реальных сокетах (аутентификация и истечение токена, изоляция клиентов, комнаты, отсутствие событий при ошибках, голосовое с проигрыванием через MinIO), всего 27 unit + 225 e2e; собранный Docker-образ проверен живым клиентом. Не сделано: события чтения (`unread` не рассылается — клиент обновляет счётчик локально), CORS для сокета (этап 12).
11. ✅ **Админ-управление** — CRUD клиентов и пользователей, сброс пароля, деактивация.
   _Итог:_ только ADMIN. **Клиенты:** `GET/POST /admin/clients`, `GET/PATCH/DELETE /admin/clients/:id`; список с поиском по названию, фильтром по типу, пагинацией и счётчиками `usersCount/vehiclesCount/requestsCount`, карточка со списком пользователей; тип можно менять, пока у клиента нет пользователей; удалить можно только «пустого» клиента (с пользователями, машинами или заявками — 409). **Пользователи:** `GET/POST /admin/users`, `GET/PATCH/DELETE /admin/users/:id`, `POST /admin/users/:id/reset-password`; создание логина подборщику/физлицу/сотруднику (публичной регистрации по-прежнему нет): email нормализуется в нижний регистр, дубль → 409, роль согласована с типом клиента (`BROKER` ↔ `COMPANY`, `INDIVIDUAL` ↔ `PERSON`, `ADMIN` без клиента), `passwordHash` наружу не отдаётся (явный `select`); фильтры списка — роль, клиент, `isActive`, поиск по email. Деактивация (`PATCH {isActive:false}`) действует **сразу**: отзываются все refresh-токены, закрываются открытые сокеты (`disconnectSockets`), а уже выданный access-токен перестаёт работать — теперь `JwtAuthGuard` и шлюз Socket.IO берут роль/клиента/`isActive` из БД, а не из токена (это закрывает ограничение «до 15 минут» из этапа 3; смена роли/привязки тоже действует сразу). Сброс пароля: пароль задаётся вручную либо генерируется временный (16 символов, возвращается один раз), все сессии завершаются. Удаление пользователя — только без истории (сообщения, заявки, вложения, журнал → 409 «деактивируйте»). Защита от потери доступа: нельзя деактивировать и удалить самого себя (так всегда остаётся хотя бы один активный админ). Смена роли пользователя не поддерживается (создайте нового). Не ограничено «один логин на компанию» (допущение §9 оставлено на уровне договорённости: модель допускает нескольких сотрудников). Проверено: 40 e2e (создание, согласованность ролей, дубли, фильтры, деактивация с access-токеном/refresh/сокетом, сброс пароля, удаление и 409, права), всего 27 unit + 265 e2e; собранный Docker-образ — полный цикл клиент → логин → деактивация → сброс → удаление.
12. ✅ **Закалка** — rate limit на логин, CORS, helmet, логирование, бэкапы БД, README с запуском и описанием env, деплой-конфиг.
   _Итог:_ **Rate limit** (`@nestjs/throttler`, guard стоит раньше JWT-guard, поэтому считаются и 401): вход — 5 попыток на связку IP+email и 30 на IP за 60 с, общий потолок 600 запросов/мин на IP, `/health` не лимитируется; ответ 429 со стандартным `Retry-After`; лимит привязан к IP, поэтому чужие попытки не блокируют владельца аккаунта; счётчики сначала были в памяти процесса, затем стали общими в Redis (см. дополнение ниже). **Заголовки и CORS:** helmet (CSP, HSTS, nosniff, frame-ancestors none), CORS и Socket.IO по белому списку `CORS_ORIGINS` (без `*`, без cookie), лимит тела 1 МБ. **Логи:** pino JSON, одна строка на запрос (метод, путь без query, статус, время, userId, `requestId`), без заголовков, тел и токенов; `X-Request-Id` принимается безопасный или генерируется и возвращается; в production Nest-логи тоже JSON; уровень — `LOG_LEVEL`; graceful shutdown по SIGTERM. **Конфигурация:** `validateEnv` в production отклоняет заглушки секретов (`change-me*`, `minio12345`) и одинаковые JWT-секреты; Swagger выключен в production по умолчанию; `TRUST_PROXY` для работы за Caddy. **Health:** `GET /health` (живость) и `GET /health/ready` (БД + S3, 503 без деталей наружу). **Деплой:** многоэтапный Dockerfile (`migrate` — применить миграции, `runtime` — API от пользователя `node` с healthcheck), `docker-compose.yml` теперь сам применяет миграции, `docker-compose.prod.yml` (Caddy с автоматическим HTTPS → API → Postgres без публичного порта, `migrate`, `backup`), `.env.prod.example`. **Бэкапы:** `deploy/backup/backup.sh` (pg_dump custom, проверка читаемости архива, атомарная запись, ротация по `BACKUP_KEEP_DAYS`) и `restore.sh` (только с `CONFIRM=yes`). **Первый админ:** `pnpm create-admin` (seed в production не используется — известные пароли). **README** с запуском, настройками, деплоем, бэкапами и безопасностью. Аудит-лог смены статусов уже реализован на этапе 5 (`VehicleStatusLog`).

   _Дополнение к этапу 12 — Redis и ffprobe (сделаны после первоначального закрытия этапа):_ **Redis 7** (`REDIS_URL`, в compose и CI; в production обязателен): общие счётчики rate limit для всех экземпляров API — `RedisThrottlerStorage` с атомарным Lua-скриптом (скользящее окно + блокировка, время берётся у самого Redis, ключи хэшированы), при недоступном Redis API не падает и не тормозит (клиент без очереди офлайн-команд, пауза 5 с, счёт временно в памяти процесса), `GET /health/ready` показывает `redis` и статус `degraded` (не 503). **ffprobe** (`FFPROBE_PATH`, в Docker-образе `apk add ffmpeg`; в production обязателен): голосовое проверяется по самому файлу — реальная длительность (в т.ч. webm из MediaRecorder без длительности в заголовке — считается по пакетам; фрагментированный mp4 из Safari; mp4 с moov в конце), лимит 5 минут применяется к фактической длительности, расхождение с заявленной больше max(2 с, 10 %) → 400, в БД сохраняется измеренное значение; в файле допустимы только аудиодорожки; формат разбирается принудительно по заявленному mime и с `-protocol_whitelist file`, поэтому плейлисты HLS/concat не заставят сервер читать файлы или ходить по URL; таймаут 15 с, не более 4 параллельных запусков, временные файлы удаляются; неработающий ffprobe при заданном пути — падение на старте, сбой ffprobe в рантайме — 503, а не 400. Проверено: 46 unit + 382 e2e (в т.ч. хранилище на реальном Redis с атомарностью под нагрузкой с двух соединений, два экземпляра API на общем Redis, 31 тест ffprobe на реальных файлах 7 форматов, SSRF-проверки, полный голосовой поток через MinIO); собранные образы dev и prod запущены вживую: ffprobe и Redis внутри контейнеров, 4 сценария голосового (верно / ложная длительность / > 5 мин / мусор), отказ production-старта без Redis и ffprobe. Найдено при проверке: `pnpm install` в Docker/CI падал на `chmod`-скриптах платформенных пакетов ffmpeg/ffprobe (на Windows их нет) — разрешены в `pnpm-workspace.yaml`. Для тестов бинарники ffmpeg/ffprobe берутся из devDependencies, системные не нужны. Проверено: 41 unit + 313 e2e (лимиты, заголовки, CORS, логи без секретов, readiness, create-admin); боевой стек реально поднят локально (HTTPS через Caddy, Swagger 404, пользователь `node`, CORS, JSON-логи, graceful stop, бэкап и восстановление в чистую базу с триггером и CHECK-ограничениями, команды из README выполнены буквально). Найдено и исправлено при прогоне: `dotenv` был dev-зависимостью и не попадал в образ; нет способа создать первого админа в боевой базе.

Фронт подключается после этапа 5–6: OpenAPI-схема уже готова, на макет не завязаны.

## 9. Принятые допущения (поменять — дёшево)

- Один аккаунт на компанию-подборщика (как в макете: «доступ один на компанию»); несколько сотрудников — позже через `User.clientId`.
- Регистрация по email с подтверждением почты (этап A2); пользователей Супер ЛК создаёт админ вручную.
- Оплату подтверждает админ сменой статуса «Получена оплата», платёжной интеграции нет.
- Файлы лежат на диске сервера (не в S3, этап A0); удаляются вручную.
- Вложения не блокируют смену статуса (флаг `STRICT_ATTACHMENTS` для строгого режима).
- машина из одобренной заявки создаётся без VIN, его заполняют позже;
- Язык интерфейса — русский; в API — английские коды, русские названия статусов отдаются справочником.

## 10. Макет и бэкенд: чего не хватает в бэкенде

Источник — README и поведение исходного макета (HTML-прототип, в репозитории не хранится; дизайн теперь в `frontend/src/styles`). Список составлен до связки фронтенда с бэкендом: пункты закрываем, когда дойдём до соответствующего экрана.

### Нужно добавить или изменить в бэкенде

1. **Статус заявки «Отклонена».** Макет: Новая → В диалоге → Одобрена **или Отклонена**, кнопка «Отклонить» у менеджера, баннер «Заявка отклонена менеджером», диалог после отклонения закрыт. В бэкенде статусы `NEW / IN_DIALOG / APPROVED`, отклонения нет.
2. **Системные сообщения в диалоге.** Макет пишет в диалог служебные строки по центру: «Менеджер одобрил вариант и создал заказ. Статус: «Ожидает оплату».», «Менеджер отклонил заявку.», «Статус машины: «…».». В бэкенде у сообщения обязателен автор-пользователь и типы только `TEXT` / `VOICE`; системных сообщений нет, одобрение и смена статуса в диалог ничего не пишут.
3. **Комментарий клиенту при смене статуса.** В форме «Сменить статус» есть необязательное поле «Комментарий для клиента»: он уходит в диалог по заявке сообщением менеджера вместе с вложениями шага. `POST /admin/vehicles/:id/status` принимает только `step` и `declarationNumber`.
4. **Смена статуса вместе с вложением одним действием.** Макет: для статусов с вложением без него статус не сохраняется (файл или фото прикладывается тут же, для шага 10 — номер декларации). У нас смена статуса и загрузка вложения — отдельные вызовы, а проверка вложений — глобальный флаг `STRICT_ATTACHMENTS` (по умолчанию выключен, допущение §9) и проверяет уже пройденные шаги, а не целевой. Нужно решение: сделать обязательность вложения штатным поведением и принимать вложение в запросе смены статуса.
5. **Первое сообщение заявки.** Макет при создании заявки сам добавляет в диалог сообщение клиента: «Новая заявка: {модель}, {год}. Бюджет {сумма}.» и комментарий с новой строки. В бэкенде заявка создаётся без сообщений, поэтому счётчик сообщений и последнее сообщение в списке были бы пустыми.
6. **Признак «Ждёт ответа» и данные для очереди заявок.** Заявка «ждёт ответа», если она не закрыта и последнее сообщение от клиента. Макету нужны: сортировка «ждущие сверху», фильтр «Ждут ответа / Все» со счётчиками, число ждущих в меню, а в строке заявки — последнее сообщение (текст или «Вложения»), его автор (Менеджер / Клиент / Система) и время. Эндпоинт очереди `GET /admin/requests` этого не отдаёт. Для клиента в списке заявок нужно последнее сообщение и «Всего заявок».
7. **Поиск и фильтры в списках машин.** Клиенту: поиск по VIN **и модели**, фильтр «Все / В пути / Готовы к выдаче» со счётчиками. Сейчас `GET /vehicles` их не поддерживает. Менеджеру: фильтр по типу владельца (Компании по привозу / Физ.лица) со счётчиками; есть `clientId`, `vin`, `step`, но нет фильтра по `ClientType`.
8. **Связь «машина → заявка» и «Обновлено».** В карточке машины макет показывает «Диалог по заявке» (заявка от …), «Обновлено» и «Вложений» (всего). У `Vehicle` нет ссылки на заявку (есть обратная `Request.vehicleId`), нет `updatedAt` и счётчика вложений.
9. **Удаление машины** менеджером с подтверждением (вместе с вложениями). Эндпоинта нет, и он упирается в неизменяемый журнал `VehicleStatusLog` (триггер запрещает удаление записей, внешний ключ запрещает удалить машину с записями). Нужна политика: мягкое удаление / архив, либо осознанное исключение для журнала.
10. **VIN: формат.** Макет — ровно 17 символов, латиница и цифры, любые. Бэкенд строже: ISO 3779, без букв I, O, Q. Реальный VIN из таможенных документов с такими буквами будет отвергнут.
11. **Добавление машины: владелец по имени.** В форме менеджер вводит тип владельца и имя строкой, а под полем подсказка «Уже есть в системе: …»; при совпадении имени машина попадает к существующему владельцу. Бэкенд принимает `clientId` или создаёт нового клиента, то есть при совпадении имени получится дубль. Нужен поиск клиента по имени или выбор из списка.
12. **Публичная проверка этапа по VIN на главной** (без входа: модель, этап, прогресс, без вложений). Публичного эндпоинта нет; нужны ограничения от перебора VIN. В README макета: «нужна ли она публично — решить с заказчиком».
13. **Регистрация.** Форма: тип кабинета, для компании — название и **ИНН** (10 или 12 цифр), для физлица — ФИО, **телефон**, email, пароль, согласие на обработку персональных данных; в README макета ещё «регистрация с подтверждением». В бэкенде публичной регистрации нет (допущение §9: аккаунты создаёт менеджер), у клиента нет полей ИНН и телефона, нет подтверждения email/телефона и фиксации согласия.
14. **Вход и пароль.** Макет: вход по email **или телефону**, пароль от 6 символов; бэкенд — только email и пароль от 8. «Забыли пароль?» — восстановления пароля нет (есть только сброс менеджером).
15. **Имя сотрудника.** В боковой панели менеджера макет показывает «Менеджер · Сотрудник компании»; у пользователя нет имени, только email.

### Этап A0. Файлы на сервере вместо S3 ✅

_Итог:_ хранилище — абстрактный `StorageService` с двумя драйверами (`DiskStorageService`, `S3StorageService`), выбор по `STORAGE_DRIVER` (по умолчанию `disk`). Остальной код и клиенты не знают, какой драйвер включён: presign → `PUT` по выданной ссылке → регистрация `key` → скачивание по `attachments[].url`. Диск: каталог `UPLOAD_DIR` (в Docker том `uploads`), ссылки подписаны HMAC (метод, ключ, срок, для загрузки ещё тип и размер), маршруты `PUT /files/upload` и `GET /files/download` без JWT, но только по подписи; загрузка потоком во временный файл с атомарной заменой, размер и `Content-Type` должны совпасть с подписанными (403), повторная загрузка по той же ссылке — 409, ключи вне формата и выход за каталог отклоняются, скачивание с `Range` (перемотка аудио и видео), `Content-Disposition` inline только для фото/видео/аудио/PDF, `Cross-Origin-Resource-Policy: cross-origin` для фронтенда на другом адресе; CORS допускает `PUT`; таймаут приёма запроса 30 минут (видео до 500 МБ). Возврат на S3 — сменой `STORAGE_DRIVER=s3` и `S3_*`, API не меняется. Изменились переменные: `S3_PRESIGN_*_TTL_SEC` → `UPLOAD_URL_TTL_SEC`/`DOWNLOAD_URL_TTL_SEC`; новые `STORAGE_DRIVER`, `UPLOAD_DIR`, `FILES_SIGNING_SECRET`, `FILES_PUBLIC_URL`; `S3_*` нужны только для `s3`. Compose и CI: MinIO вынесен в профиль `s3`, CI дополнительно гоняет контракт хранилища на S3. Бэкап: `backup.sh` кладёт рядом с дампом архив файлов (`BACKUP_UPLOADS`), `restore-uploads.sh` восстанавливает (нужен `CONFIRM=yes`). Проверено: 51 unit + 412 e2e на диске (в т.ч. 30 тестов дисковых ссылок и загрузка файла 3 МБ через боевой адаптер при лимите JSON 1 МБ), те же тесты хранилища, загрузок, машин, сообщений, голосовых и realtime (162) — на драйвере S3 с MinIO; собранный Docker-образ вживую: загрузка, отказ при чужом типе, вложение в сообщение, скачивание байт в байт, `Range` 206, файлы принадлежат `node`; бэкап и восстановление архива файлов выполнены в контейнерах; `docker-compose.prod.yml` без `FILES_SIGNING_SECRET` не стартует. Не проверено: GitHub Actions (шаг с S3 в CI не запускался).

Заменяем S3/MinIO на диск сервера (каталог `UPLOAD_DIR`, том Docker). Файлы удаляются вручную. Хранилище проектируем за интерфейсом (`FileStorage` с реализациями «диск» и «S3», выбор по env `STORAGE_DRIVER`), чтобы вернуться на S3 заменой драйвера без правок остального кода: сервисы вложений и сообщений знают только ключ объекта, метаданные и способ выдачи ссылки (S3-драйвер отдаёт presigned URL, дисковый — защищённую ссылку API). Действующая S3-реализация этапа 4 остаётся как второй драйвер (тесты на MinIO сохраняются, но не обязательны в CI). `StorageService` сохраняет интерфейс для остального кода: загрузка идёт через API (`POST /uploads` с типом и размером, тело — файл; лимиты и список mime по видам прежние, ключ `{kind}/{userId}/{uuid}.{ext}`), выдача — защищённым `GET /files/:key` с проверкой доступа (владелец клиента или админ) либо короткоживущей подписью в URL; в `attachment.url` приходит такая ссылка. Регистрация вложения берёт размер и тип из файла на диске; ffprobe читает файл напрямую. В compose, CI, `.env*`, README по умолчанию дисковый драйвер (MinIO и `S3_*` — только для драйвера S3); в бэкап (`deploy/backup`) добавляем каталог файлов, в `restore.sh` — его восстановление. Тесты: все e2e, что шли через MinIO, переводятся на реальный диск (временный каталог), плюс доступ к чужому файлу → 404, подмена пути (`../`), повторная регистрация ключа.

### Этап A. Бэкенд под макет

1. ✅ **Статус заявки `REJECTED`** (§10 п. 1): значение enum + миграция, `POST /admin/requests/:id/reject` (из `NEW`/`IN_DIALOG`, повтор — идемпотентно), запись в диалог закрыта (409, как у `APPROVED`), событие `request.updated` с причиной `REJECTED`, фильтр очереди. Тесты: права, изоляция, повтор, запись после отклонения.
   _Итог:_ отклонение под той же блокировкой строки, что у `approve` и записи сообщений: одобренную заявку отклонить нельзя (409), отклонённую одобрить нельзя (409), при одновременных `approve` и `reject` побеждает ровно один; закрытая заявка (`APPROVED`/`REJECTED`) не принимает сообщения и голосовые (409), но читается и отмечается прочитанной; фильтр `status=REJECTED` у клиента и в очереди. Проверено: 14 e2e отклонения (права, идемпотентность, гонки, диалог, фильтры, изоляция) и событие по сокету; всего 51 unit + 426 e2e.
2. ✅ **Системные сообщения** (п. 2): тип `SYSTEM`, автор не обязателен. Пишутся в той же транзакции при одобрении, отклонении и смене статуса машины, связанной с заявкой; тексты как в макете. Не считаются непрочитанными, `isMine=false`, приходят по сокету. Тесты: тексты, транзакционность, счётчик непрочитанного.
   _Итог:_ `MessageType.SYSTEM`, `Message.authorId` необязателен, CHECK в миграции: автора нет ровно у служебных сообщений; внешний ключ автора — RESTRICT (пользователя с сообщениями по-прежнему не удалить). Тексты: «Менеджер одобрил вариант и создал заказ. Статус: «Ожидает оплату».», «Менеджер отклонил заявку.», «Статус машины: «{полное название этапа}».». Строка пишется в той же транзакции, что и изменение, и только при реальном изменении (повторное одобрение/отклонение, повтор того же этапа ради номера декларации и отказ не пишут ничего); у машины без заявки диалога нет — ничего не пишется. В API `author: null`, `isMine: false`, вложений и ссылок нет; по сокету уходит `message.created` после коммита. Служебные строки не считаются непрочитанными и не меняют статус заявки; создать `SYSTEM` через `POST /requests/:id/messages` нельзя (400). Проверено: 14 e2e служебных сообщений (тексты, один раз при гонке, откат, видимость, счётчики, CHECK) и событие по сокету; существующие тесты, считавшие «сообщения диалога», теперь считают только сообщения людей. Всего 51 unit + 441 e2e.
3. **Смена статуса с комментарием и вложением одним действием** (пп. 3–4): `POST /admin/vehicles/:id/status` принимает `comment?` и `attachments?[]`. Комментарий уходит сообщением менеджера в диалог связанной заявки вместе с вложениями, всё в одной транзакции. Вложение обязательно, если у целевого шага оно ожидается (шаг 10 — номер декларации) и ещё не прикреплено; шаги без вложения сохраняются сразу. Это заменяет глобальный `STRICT_ATTACHMENTS` (флаг убираем, тесты строгого режима переписываем под новое правило, а не ослабляем).
4. **Первое сообщение заявки** (п. 5): создание заявки пишет сообщение клиента «Новая заявка: {модель}, {год}. Бюджет {сумма}.» + комментарий с новой строки, в той же транзакции.

### Этап A2. Почта, регистрация и уведомления

1. **Почта.** Отправка писем (SMTP, `SMTP_URL` и `MAIL_FROM` в env; в production обязательны, в dev/тестах — транспорт-заглушка, письма видны в логах/тестах). Письма уходят после коммита транзакции, сбой отправки не ломает запрос и пишется в лог.
2. **Регистрация по email.** `POST /auth/register {type: COMPANY|PERSON, name, inn? (для компании, 10 или 12 цифр), phone, email, password (≥ 8), consent: true}` создаёт клиента (новые поля `inn`, `phone`, `consentAt`) и пользователя (`BROKER` / `INDIVIDUAL`); вход закрыт, пока почта не подтверждена. `POST /auth/verify-email {token}`, `POST /auth/resend-verification`; токен одноразовый, живёт ограниченное время, хранится хешем; вход до подтверждения — 403 с кодом `EMAIL_NOT_VERIFIED`. Лимиты частоты как у входа; ответ не раскрывает, занят ли email. Пользователей `ADMIN` по-прежнему создаёт только админ (`/admin/users`), публично роль не выбирается. Тесты: валидация (ИНН, телефон, согласие), дубль email, подтверждение, повторное использование и истечение токена, вход до и после подтверждения, лимиты.
3. **Уведомления о смене статуса (email, опция).** Физ.лицо получает письма по умолчанию на свой email (может отключить). Для подборщика: в карточке машины подборщик задаёт email своего конечного клиента и включает «уведомлять» (`PATCH /vehicles/:id/notifications {email?, enabled}`, только владелец машины; по умолчанию выключено) — письма о смене статуса уходят на этот email. Письмо: название нового этапа и ссылка в кабинет, русский текст, без вложений. О сообщениях в диалоге письма не шлём — для них push (п. 4). Тесты: кому уходит и кому нет, выключенные уведомления, чужая машина, сбой почты.
4. **Push-уведомления о сообщениях в диалоге (Web Push).** Диалог идёт между владельцем заявки (подборщик или физ.лицо) и сотрудниками Супер ЛК (`ADMIN`); автору push не приходит, чужие клиенты не получают ничего. Написал сотрудник — push устройствам владельца заявки. Написал владелец заявки: пока на заявку никто не ответил — push всем сотрудникам Супер ЛК; есть ответственный — только ему, а если он не ответил в течение часа (`PUSH_FALLBACK_MINUTES`, по умолчанию 60), сообщение снова уходит всем. Ответственный — сотрудник, который ответил в заявке последним (`Request.assigneeId`, проставляется при каждом сообщении сотрудника; ручного переназначения нет). Новым сообщением владельца отсчёт часа начинается заново; повторный push всем отправляется один раз на сообщение. В очереди и в диалоге виден ответственный («ведёт: …»). Таблица `PushSubscription` (пользователь, endpoint, ключи, устройство), `GET /me/push/public-key`, `POST/DELETE /me/push-subscriptions`; ключи VAPID в env (в production обязательны), библиотека `web-push`; недействительные подписки (404/410) удаляются; текст короткий («Новое сообщение по заявке Haval Jolion, 2023», без содержимого), клик открывает диалог. Push уходит после коммита транзакции, сбой не ломает запрос; подписка работает только по HTTPS (localhost — исключение). Тесты: кому уходит и кому нет, автор, чужой пользователь, удаление протухшей подписки, права на подписки.
5. **Непрочитанное.** Счётчик непрочитанных по заявкам уже есть (`unreadCount`, `GET /requests/unread-count`); для менеджера добавляем общий счётчик по всем заявкам. Доработок схемы не требуется.

### Этап C. Вход и сессия

Форма входа → `POST /auth/login`, роль и клиент из `GET /me` (`BROKER`→компания, `INDIVIDUAL`→физ.лицо, `ADMIN`→Супер ЛК), выход → `/auth/logout`, восстановление сессии при открытии, права и редиректы по реальной роли. ### Этап D. Кабинет клиента

Список машин (поиск, фильтры, счётчики с сервера), карточка машины (история статусов, вложения по ссылкам на файлы сервера, «Диалог по заявке»), список заявок, новая заявка. Счётчики в меню — с сервера. Уведомления: у подборщика в карточке машины блок «Уведомлять клиента» (email клиента + переключатель), у физ.лица — настройка на странице кабинета (в стиле существующих строк-переключателей). Рядом со вкладкой «Заявки» (диалоги) в меню показывается число непрочитанных сообщений (тем же значком `.cnt.hot`, что у очереди менеджера; если непрочитанных нет — значка нет); то же у менеджера для «Входящих заявок». В боковой панели — кнопка «Включить уведомления» (запрос разрешения браузера и подписка на push, оформление как у соседних кнопок).

### Этап E. Диалог

Сообщения (курсорная пагинация «вверх»), отправка, системные сообщения, отметка прочитанного, вложения: выбор файла → загрузка на сервер (`POST /uploads`, этап A0) → регистрация в сообщении. В макете «Прикрепить фото или ссылку» только имитируется; настоящий выбор файла и ввод ссылки добавляем аккуратно, в том же стиле (кнопки, поля и чипы из существующего дизайна). Под сообщением клиента-подборщика появляется блок «Уведомления клиенту» в карточке машины (переключатель и email, этап D). Голосовые в макете не нарисованы — в этот этап не входят (бэкенд готов, экран — в бэклог).

### Этап F. Супер ЛК

Все машины (фильтры, поиск по VIN), добавление машины (владелец: сначала ищем клиента по точному имени и типу среди `/admin/clients`, если нет — создаём нового, чтобы не плодить дубли), карточка машины: заполнение VIN, смена статуса с комментарием и вложением одним запросом (загрузка файла, номер декларации), очередь заявок («ждут ответа»), ответ в диалоге, «Одобрить и создать заказ», «Отклонить». Удаление машины и публичная проверка по VIN — не подключены (бэклог, показывают «Пока недоступно»).

### Этап G. Realtime

`socket.io-client`: подключение по access-токену, переподключение с новым токеном, комнаты заявок, события `message.created`, `request.updated`, `vehicle.status_changed` обновляют кэш; индикатор непрочитанного в меню.

### Этап H. Проверка и выкатка

Сквозной прогон всех сценариев на живом стеке (Docker Compose: API + Postgres + Redis + фронт, файлы на томе) на тех же размерах экрана и в обеих темах, что при переносе макета; тесты слоя данных (обновление токена, разбор ошибок). Dockerfile фронтенда, фронт в `docker-compose.prod.yml` за Caddy, `README`.
