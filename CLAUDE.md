# Green Angle — правила работы

Подробный план и стек — в [PLAN.md](PLAN.md). Прогресс по этапам отмечать там же.

## Инструменты

1. **Нельзя создавать вручную то, что генерируется готовыми командами.** Скелеты проектов
   (Next.js, React, NestJS и т. п.), модули/контроллеры/сервисы NestJS, миграции Prisma,
   конфиги, которые создаёт CLI, — только через официальные генераторы
   (`nest new`, `nest g module|controller|service|resource`, `pnpm create next-app`,
   `pnpm create vite`, `prisma init`, `prisma migrate dev` и т. д.). Руками правим уже
   сгенерированное содержимое, но не воспроизводим структуру файлов по памяти.
2. **Пакетный менеджер — только pnpm.** Не использовать npm и yarn (`pnpm add`, `pnpm install`,
   `pnpm dlx` вместо `npx`). Lock-файл — `pnpm-lock.yaml`; `package-lock.json` и `yarn.lock`
   в репозиторий не добавлять.
3. **Версии зависимостей согласовывать.** После `pnpm add` проверять `pnpm peers check`;
   пакеты экосистемы (например, `@nestjs/*`) держать на одной мажорной версии.
   - **Актуальный стек.** Node 24 LTS (Nest 12 требует ≥ 22.22), NestJS 12 (ESM: в относительных
   импортах расширение `.js`), Vitest вместо Jest, ESLint 10 + Prettier (oxlint из генератора заменён по решению пользователя), TypeScript 6,
   Prisma 7.10.x стабильный (тег `latest` у CLI может указывать на RC — ставить версию явно).

## Процесс работы с ИИ

4. **Работать строго по PLAN.md.** Один этап за раз, без «заодно» из следующих этапов.
   Завершив этап — отметить его в PLAN.md (✅ + краткая заметка), не раньше.
5. **Сначала понять, потом менять.** Перед правкой прочитать существующий код и соседние
   файлы; следовать принятому стилю, именованию и структуре. Не угадывать API библиотек
   по памяти — сверяться с установленной версией и документацией.
6. **Небольшие проверяемые шаги.** После каждого значимого изменения запускать
   `pnpm build`, `pnpm lint`, `pnpm test` (и e2e, если затронуто). Этап не считается
   завершённым, пока «Готово, когда» из PLAN.md не проверено реально.
7. **Тесты пишутся вместе с кодом.** Особенно для RBAC и изоляции данных по `clientId`,
   транзакций (одобрение заявки) и идемпотентности. Не ослаблять и не удалять тесты,
   чтобы они проходили.
8. **Честная отчётность.** Если что-то не запускалось, упало или пропущено — сказать об
   этом прямо. Не утверждать «работает», не проверив.
9. **Минимальный объём изменений.** Не рефакторить чужой код без запроса, не добавлять
   лишние абстракции, зависимости и «на будущее». Без мёртвого кода и закомментированных
   кусков.
10. **Деструктивные и внешние действия — только с подтверждения.** Удаление файлов и
    данных, `git push`, `git reset --hard`, миграции на общих БД, публикация чего-либо
    наружу. Коммиты — см. правило 14.
11. **Секреты.** Никаких ключей и паролей в коде и в git: только `.env` (в `.gitignore`)
    и `.env.example` с безопасными заглушками.
12. **Не гадать при неоднозначности.** Если решение за пользователем (продуктовое, по
    стеку, по допущениям из PLAN.md §9) — спросить кратко с рекомендацией; если
    обратимо и очевидно — выбрать разумный вариант и указать это в отчёте.
13. **Язык.** Общение и документация — на русском; код, идентификаторы, коммиты и
    API-коды — на английском.
14. **Коммит после каждого реализованного функционала.** Законченный кусок (фича, модуль,
    этап, значимое исправление) — отдельный коммит, после зелёных build/lint/test. Сообщения
    в формате Conventional Commits на английском (`feat:`, `fix:`, `chore:`, `test:`,
    `docs:`), одна логическая тема на коммит. `git push` — по-прежнему только с подтверждения.
15. **Файлы создавать и править только через Write и Edit.** Не писать файлы через
    `cat > file <<'EOF'`, `echo >`, `sed -i` и подобные трюки в Bash. Bash/PowerShell — для
    запуска команд (pnpm, nest, docker, git), а не для записи содержимого файлов.

16. **Никаких упоминаний Claude/ИИ-соавторства.** Ни в коммитах (без `Co-Authored-By`,
    «Generated with Claude Code» и т. п.), ни в PR, коде, комментариях и документации.

## Структура репозитория

- `backend/` — NestJS API (pnpm, свой `package.json` и lock-файл).
- `frontend/` — Next.js (pnpm, SCSS). Дизайн берётся **только** из `huatech-handoff/` (презентация PDF — лишь иллюстрация, из неё ничего не переносить). Сначала точный перенос макета без бэкенда, потом связка с API.
- `huatech-handoff/` — макет (прототип `prototype/index.html`, `design-system/`): только читать, не менять.
- Корень: `PLAN.md`, `CLAUDE.md`, `docker-compose.yml`, `.gitignore`, `.github/`.
- Команды pnpm запускать из `backend/` (или `frontend/`), не из корня.
